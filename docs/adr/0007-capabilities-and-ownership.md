# Capabilities as the config unit; ownership in teams/ and owners.yml

Config is grouped by business capability (`capabilities/<cap>/`), not by team, and several teams can own apps in one capability. Teams are defined once in `teams/<team>.yml` (GitHub team and IdP group). `owners.yml` at the capability level, optionally replaced per app, names the owning teams. An app's owners approve its code changes and can promote it to any stage. From that, CI generates `.github/CODEOWNERS` and one Kargo role per owning team (the `promote` verb on that team's app stages, bound by OIDC group claim). A stage that deploys to a `prod` target can't `autoPromote`.

## Considered Options

- **Per-stage ownership** (e.g. a different team owns prod): deferred. With rendered manifests, a merge only creates Freight. Prod changes only when someone with promote rights on prod promotes, so the promotion gate is the real control. Per-stage edit control would need either one file per stage (which still misses base-layer changes) or a custom review check.
- **Ownership declared in team files**: rejected. That would scatter the answer to "who owns X" across files and need conflict checks.

## Consequences

- `owners.yml` and `teams/` are platform-approved, because whoever can edit them controls promotion.
- CODEOWNERS is regenerated by CI on main, not checked in the PR (superseded by ADR 0022: authors run `mise run codeowners`, CI checks it), so nobody needs local tooling (Mac/Windows). An ownership change takes effect from the next PR.
- The CODEOWNERS template keeps the platform-only lines last, because the last matching line wins.
- Future: `managers` in `owners.yml`, who can approve any change in a capability.
