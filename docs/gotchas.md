# Gotchas

Non-obvious failures hit while building this, with the fix in place. Check here before changing networking, auth, or the infra task.

## Networking

- **Tailscale holds `*:443` on the host.** kind binding `0.0.0.0:443` fails with "address already in use". Fix: `platform/cluster/kind.yaml` binds `127.0.0.1` and `::1` only.
- **`::1` broken on kind's default network.** The `kind` docker network is dual-stack, so Docker Desktop forwards `::1` to the node's IPv6, where the IPv4-only cluster has no NodePort. Browsers resolve `*.localhost` to `::1` first. Fix: `mise run up` creates an IPv4-only `kargo-demo` network (`KIND_EXPERIMENTAL_DOCKER_NETWORK`).
- **`keycloak.localhost` inside the cluster.** The issuer must be the same URL for the browser and in-cluster clients (kargo-api, argocd-server). A CoreDNS `rewrite` (`dns.Hub` in `platform/cli/internal/dns`) points it at the Traefik service.
- **curl in pods ignores that rewrite**: curl resolves `*.localhost` to loopback itself. Test in-cluster DNS with `busybox` `nslookup`/`wget`.

## Keycloak

- **Realm file must be named `<realm>-realm.json`** (`kargo-realm.json`), or Keycloak exits with "File name / realm name mismatch".
- **Imported users get no default roles.** Users need `realmRoles: [default-roles-kargo]` (includes `offline_access`). Without it the Kargo UI's token exchange fails, and because Keycloak's error response has no CORS header, the browser shows a misleading **CORS error**. Check Keycloak logs for the real error.
- **Issuer is plain `http://`**, so kargo-api/argocd-server need no custom CA. Both UIs accept it.
- **Dev mode, no persistence.** The realm is re-imported on every start; the kustomize `configMapGenerator` hash restarts Keycloak whenever the realm file changes. Edits made in the console are lost.
- **Scripted logins with curl**: Keycloak sets `Secure` cookies, which curl drops over `http://` (browsers keep them on `*.localhost`). Pass the cookies manually with `-H Cookie:`. The `kargo` client allows the password grant for quick token tests.

## Argo CD

- **Ingress never turns Healthy.** NodePort Traefik publishes no address, so Argo CD leaves an `Ingress` Progressing forever. Expose UIs with Traefik `IngressRoute` instead (Argo CD's is in `extraObjects`).
- **Bootstrap skips `extraObjects`.** At first install the Traefik CRDs don't exist yet; the self-managing `argocd` app adds the IngressRoute later. Otherwise keep `platform/infrastructure/argocd/values.yaml` identical for bootstrap and self-management.
- **Stale status after apply.** Right after `kubectl apply` of a changed Application, Argo CD can still report the old `Synced`. `argocd.WaitApp` (`platform/cli/internal/argocd`) requests a refresh and waits for it to be processed before waiting on Synced/Healthy.
- **Stale health after Argo CD restarts itself.** Changing Argo CD's own config can leave another app stuck `Progressing`. Fix: `kubectl -n argocd annotate app <app> argocd.argoproj.io/refresh=hard --overwrite`.
- **Kargo chart is OCI** (`ghcr.io/akuity/kargo-charts`); it needs the `enableOCI` repository entry in Argo CD values.

## Kargo

- **Stage names max 63 characters.** Kargo 1.12 labels every PromotionRequest with the unshortened Stage name (`pkg/api/promotion_request.go`), so a longer Stage is created but every promotion into it fails. Lint rejects rendered Stage names over 63 (`stageNameErrors` in `delivery.cue`). Argo CD Application names aren't capped (annotation tracking allows 253).
- **REST API** is `/v1beta1/...` (e.g. `GET /v1beta1/projects`, `POST /v1beta1/resources`). Connect-style paths return 405.
- **Role claims** map via annotation `rbac.kargo.akuity.io/claims: '{"email":[...]}'` on the project's `kargo-admin` / `kargo-promoter` / `kargo-viewer` ServiceAccount.
- **Default `additionalScopes` is `[groups]`**, which the Keycloak realm doesn't define; it's overridden to `[]`.
- **Creating a resource with no `metadata.name` returns 500, not 403** (Kargo bug: name checked before authz). Permissions still hold.
- **The gitops-only policy keys on the `kargo-api` ServiceAccount.** All UI/API writes are made by that SA, so the policy covers every user, admins included. Writes from `kubectl` as cluster admin are the intended path and are not affected.
- **Terraform module discovery (ADR 0021) fails for the whole repo on one bad tag.** The `image` subscription fetches each candidate tag's manifest + config: an OCI index (`empty V2 manifest list or OCI index is not supported`) or a non-JSON `--config` breaks discovery of every tag. Push single manifests with oras' default empty config (`mise run tf-module-push`). Never add `platform` to a module subscription: artifacts have no platform, so every tag is filtered out.
- **ghcr rejects fine-grained PATs** (`denied: permission_denied: The token provided does not match expected scopes` on push, after `Login Succeeded`). GitHub Packages only takes classic tokens; `tf-module-push` uses the gh CLI token: `gh auth refresh -h github.com -s write:packages` once.
- **A new ghcr package is private.** Kargo has no registry credential, so the Warehouse can't discover a private module (401). After the first `mise run tf-module-push`, set `tf-bucket` to public in the package settings (the push links it to this repo via `org.opencontainers.image.source`).
- **Example promotions call GitHub for real** (`gha-trigger` step). Use a throwaway Stage pointed at an in-cluster echo server when testing step behaviour.

## gitops-cd (rendered capabilities)

- **Push before `up`.** The root app (`platform/bootstrap/root.yaml`) syncs `platform/appsets/` from GitHub `main`, add-ons read their values/manifests from `main`, and Kargo pushes `env/<cap>/<app>/<target>` branches there. Without the repo pushed, `root` shows ComparisonError, no add-on app is ever generated (`infra` times out in `wait_app`), and promotions fail at `git-push`.
- **Kargo git creds are shared.** The Kargo chart creates `kargo-shared-resources` (`global.sharedResources.namespace`); a `kargo.akuity.io/cred-type: git` Secret there serves every project. `mise run creds` writes it from fnox using the GitHub App (`githubAppID`, `githubAppInstallationID`, `githubAppPrivateKey`). Argo CD gets no repo secret: the repo is public, and a bad credential there breaks Argo CD's reads (`failed to list refs: authentication required`).
- **GHA targets (`deployWith: gha`, ADR 0020) fail at `dispatch`.** 401 `Bad credentials`: `kargo-shared-resources/github-actions` missing or the PAT expired; re-run `mise run creds`. 404: the workflow file isn't in `<repo>/.github/workflows/` at `ref`, or the PAT lacks `Actions: read and write` on that repo. 422: the workflow has no `workflow_dispatch` trigger on `ref`, or an input name doesn't match. A 204 means `return_run_details` was ignored (GHES), which fails the step.
- **Pre-deploy checks (`pre-<n>` steps, ADR 0028) fail at `pre-<n>::dispatch`.** 404: the check file isn't in the app's `sourceRepo` under `.github/workflows/` at `ref`, or the PAT doesn't cover that repo (`Actions: read and write` on every `sourceRepo`). 422: the workflow doesn't declare an input Kargo sends (`capability, app, stage, target, commit`, and `image`/`module`: declare both, optional). They run on every Promotion of a prd target Stage, rollbacks and `kargo-restore` included: a failing check blocks a rollback too. At `pre-<n>::wait`, "exceeded <timeout>" means the run took longer than the check's `timeout`; it keeps running on GitHub.
- **GHA target Stages always show Healthy** after a successful promotion. With no `argocd-update`, no health check is registered, and Kargo counts zero checks as Healthy. That's expected, not a status bug; for a real signal add verification (AnalysisTemplate), as ADR 0020 describes.
- **Don't define `clientScopes` in the realm JSON.** That replaces Keycloak's defaults (profile, email…) and drops the `email` claim all access depends on (ADR 0011). Requesting a scope the realm lacks (e.g. Kargo's default `groups`) fails login, so Kargo keeps `additionalScopes: []`.
- **Emails must match exactly.** Kargo claim mapping and Argo CD `scopes: [email]` compare strings as-is, so `owners.yml` only accepts lowercase emails; the IdP must issue lowercase `email` claims too.
- **Sync `Unknown` until a target's first promotion.** Each Argo CD app tracks `env/<cap>/<app>/<target>`, which Kargo creates on the first promotion of that target stage. Until then: `ComparisonError: unable to resolve ... revision not found`, sync `Unknown`, health `Healthy` (no resources). Expected for prod, which never auto-promotes. Destination `Unknown` in the UI for non-admins is separate: teams have no `clusters, get`.
- **Kargo Stages are empty after `up`.** Stage history lives only in the hub's etcd; GitHub keeps the deployed state. Run `mise run kargo-restore` (`docs/operations.md`).
- **Old stage branches are orphaned.** Before ADR 0012 branches were `env/<cap>/<app>/<stage>`; nothing uses them now. Delete them on GitHub by hand (Kargo/CI never delete branches).
- **Render the Kargo project namespace.** Argo CD dry-runs every resource before applying any, so leaving `kargo-<cap>-<app>` for Kargo to create from the Project fails the whole first sync forever. The renderer emits `Namespace kargo-<cap>-<app>` labeled `kargo.akuity.io/project: "true"` (Kargo adopts it); `rendered-kargo` keeps a sync retry as a backstop. (`kubectl apply --dry-run=server` still reports NotFound for these; Argo CD doesn't.)
- **AppProjects whitelist `Namespace`.** Generated Applications use `CreateNamespace=true`, which needs the cluster-scoped `Namespace` kind allowed in the AppProject.
- **Kargo project names are visible to all users with any project.** `GET /projects` needs cluster-scoped `list projects` (`kargo-user`), and Kargo 1.12 only filters by access with `?mine=true` (UI "My projects"). Contents stay limited to projects where the user is mapped to a ServiceAccount (`viewers`, `promote-<stage>`).
- **Kargo global ServiceAccounts.** `users-<cap>` SAs live in `kargo-shared-resources`, which must be listed in `api.oidc.globalServiceAccounts.namespaces`, or their claims never match.
- **GitHub App 401 "A JSON web token could not be decoded"** (Warehouse: `error minting installation access token`): the private key doesn't belong to the App ID (wrong App, or a revoked/regenerated key). Generate a new key in the App settings and `fnox set GITHUB_APP_PRIVATE_KEY`.
- **Approving Freight checks `promote`, not a separate verb.** `POST /v1beta1/projects/<p>/freight/<f>/approve?stage=<s>` (the UI's "Manual approval required") is allowed for anyone with `promote` on the Stage, and the kargo-api ServiceAccount writes the status itself. RBAC and admission can't restrict it; the break-glass guard does (ADR 0013). If no one but admins can approve, the Stage has no `example.com/break-glass` annotation yet (not rendered onto branch `rendered` yet).
- **Promote needs two grants.** Kargo's promote API checks `promote` on the Stage *and* creates the Promotion as the user, so owner roles also need `create` on `promotions` (as Kargo's built-in `kargo-promoter` Role has). Missing it: `promotions.kargo.akuity.io is forbidden: create is not permitted`.
- **"Auto-promotion paused" with nothing in git.** That's an auto-promotion hold (Kargo 1.12), not config. A manual Promotion of Freight other than what Kargo would auto-promote (e.g. a rollback to older Freight) pauses auto-promotion for that Stage + Warehouse, so the next auto-promotion doesn't undo it. It lives in Stage `status.autoPromotionHolds` (who, which Freight, which Promotion; `effectiveAutoPromotionHolds` is what's in force), so the gitops-only policy allows it and Argo CD sees no drift. It stays until a promoter releases it ("Resume auto-promotion" in the UI) or promotes the newest Freight. Find held Stages: `kubectl -n kargo-<cap>-<app> get stages -o json | jq -r '.items[] | select(.status.effectiveAutoPromotionHolds != null) | .metadata.name'`. `autoPromote` in `stages/*.yml` still decides whether a Stage auto-promotes at all.
- **Failed auto-promotions aren't retried.** Kargo auto-promotes a given Freight once; if that Promotion errors (e.g. bad git creds), promote it manually or wait for new Freight.
- **Browser TLS warning on `*.localhost`.** Traefik's default cert is self-signed unless the `local-tls` secret (`mise run certs`, mkcert) exists. First `mkcert -install` asks for your macOS password to trust the CA in the keychain (Chrome/Brave; Firefox would need `nss`). Restart the browser if an old tab still warns. `*.localhost` wildcards are rejected by browsers, so hosts are listed explicitly: a new UI host must be added in `certs.Run` (`platform/cli/internal/certs`).
- **Every Argo CD has an app named `root` (and `argocd`).** Hub and region `kubectl` calls need explicit `--context`. Until CI renders `rendered/argocd/{deploys,projects}/<region>/` and `rendered/infrastructure/regions/` onto branch `rendered` (first push to `main` after a fresh repo/fork), `argocd-projects` shows ComparisonError (revision or path not found) and the hub has no `kargo-ctrl-<r>`/`argocd-ui-<r>`, so `mise run up`/`infra` time out waiting for them. Wait for CI's first render (`git ls-remote origin rendered`), then re-run.
- **Workload apps lag on a fresh `up`.** The `workloads` AppSet can generate an Application before `argocd-projects` has created its AppProject; Argo CD rejects it (`ApplicationSet status: ... AppProject not found`) until the AppSet requeues (git generator, ~3 min). Harmless; `infra` doesn't wait for workloads. To skip the wait: `kubectl --context kind-region-<r> -n argocd annotate applicationset workloads argocd.argoproj.io/application-set-refresh=true`.
- **kubelet pulls images one at a time by default.** One slow image (e.g. a stalled pull) blocks every pod behind it. `platform/cluster/{kind,region}.yaml` set `serializeImagePulls: false`. A `registry:2` pull-through cache was tried and dropped: it stalled on large ghcr blobs and can't proxy `ecr-public.aws.com` (auth).
- **Root app applied before Argo CD runs idles ~2-3 min.** The application-controller only picks it up at the next periodic reconcile. `infra` (`argocd.ApplyRoot`) waits for the controllers, applies it, then forces a refresh.
- **Kargo pods wait ~2 min after their certs exist.** All add-ons start together, so kargo's pods start before cert-manager issues `kargo-*-cert`; kubelet's mount retry has backed off by then. `infra` (`kargo.KickCertPods`) recreates Pending pods mounting a `*-cert` Secret (plain or projected volume) once the Certificates are Ready.
- **An app never appears: check the ApplicationSet.** `kubectl -n argocd get applicationset <name> -o yaml` → `status.conditions` (e.g. `missingkey` template errors, git generator path not found). A cluster generator matches nothing if the in-cluster Secret lacks the `example.com/*` labels (helm values `configs.clusterCredentials`).
- **`_o.promoters.<stage>: field not allowed` on a valid owners.yml.** CUE (v0.17) closedness of `#Promoters` (fields from `for n in _stageNames`) depends on evaluation order, because `stages` depends on deploys (prod autoPromote rule). Render outputs must read owner values from the raw file (`_o` in `owners.cue`); only `capOwners` validates against `#Owners`. Seen when Argo CD roles first referenced per-app emails (ADR 0029).

## Kargo shards (regions)

- **Stage shard is `spec.shard`, not the label.** `kargo.akuity.io/shard` is derived from `spec.shard` by a webhook; setting only the label does nothing (the hub controller or nobody picks the Stage up).
- **Hub shard release needs `dataPlane.install: false`.** `kargo-ctrl-<shard>` (second chart release in ns `kargo`) otherwise renders the shared Roles/CRDs again and collides with the main `kargo` release. It must be installed after `kargo` (it binds that release's ClusterRoles/Role).
- **Regional controller needs events RBAC in `argocd`.** `argocd-update` records events on the Application; the chart's Argo CD RBAC lacks them (`events is forbidden`). Added as `extraObjects` in the `valuesObject` of `platform/appsets/addons/kargo-shard.yaml`.
- **Token handoff is host-side.** `mise run kargo-shards` copies hub Secret `kargo/kargo-controller-<shard>-token` into a kubeconfig in region Secret `kargo/kargo-hub-kubeconfig` (server `https://kargo-demo-control-plane:6443`, docker network). Token change restarts the regional controller; the hub never holds region creds.

- **`argocd-update` `desiredRevision` must be a commit SHA, not a branch.** Argo CD's sync result records the commit, so `desiredRevision: main` never matches and the Promotion stays `Running` forever (log: `sync result revision does not match desired revision`). Use `${{ commitFrom("<repoURL>").ID }}` (argument is the repo URL, not the Warehouse).

## Regional Argo CD UI / OIDC
- **Regional UIs go through the hub Traefik.** Only the hub binds host 443. `argocd-<region>.localhost` is an IngressRoute (`platform/appsets/addons/argocd-region-hub.yaml`, Application `argocd-ui-<region>`) to an ExternalName Service `region-<r>-control-plane:30081` (argocd-server NodePort). Docker DNS keeps the name valid across restarts; Traefik needs `providers.kubernetesCRD.allowExternalNameServices: true`. The hub holds no region credentials (plain HTTP proxy).
- **Regions reach keycloak.localhost via `mise run region-dns`.** Hub Traefik is at `<hub container IP>:30080` on the docker network, not port 80. Each region gets a CoreDNS rewrite to Service `kube-system/hub-traefik` (selectorless, port 80 -> EndpointSlice hubIP:30080). The IP is re-resolved on every `infra` (it can change after a docker restart; rerun `mise run infra` or `mise run region-dns`).
- **Per-region values live in the AppSet.** Region bits (domain, OIDC client, cluster labels) are the `valuesObject` of `platform/appsets/addons/argocd-region.yaml` with `{{.values.region}}`; `infra` seds that token for the first `helm install`, so keep it literally `{{.values.region}}`. Keycloak `argocd-<region>` clients and Kargo `api.argocd.urls` are generated by `mise run regions` from `clusters.cue`; do not hand-edit them in `kargo-realm.json`/kargo values. New region UI host also needs `mise run certs` (done by `infra`).
- **Kargo deep links**: default shard ("") has no mapping (control-flow Stages have no Argo CD apps; hub Argo CD runs only infrastructure).
- **Freight from before ADR 0016 can't be promoted.** It has no image (`imageFrom(...)` fails), or its commit predates the current layout (`yaml-update`: no `deployment.yaml`; earlier `kustomize-set-image`: "could not find any Kustomization files"). Assemble new Freight from a commit rendered after the change (Warehouse → newest commit + image tag). If the Warehouse shows no images, the repo has no SemVer tags matching `imageConstraint` (`latest` is ignored).
- **`yaml-update` only sees a file's first YAML document** (Kargo 1.12, `pkg/yaml`: one `yaml.Unmarshal` into a node). Keys in later documents of a multi-doc file aren't found. That's why the Deployment is rendered to its own `deployment.yaml`.
